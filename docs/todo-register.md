- **TODO-03** 填报截止前学生可撤回志愿并重新提交；每次提交生成一个新版本，历史版本只增不删；填报截止时以最后提交的版本锁定，作为后续轮次处理依据。学生本人可查看本人的历史版本。

- **TODO-52 管理员业务授权管理（2026-10-03 已确认）**：只有总管理员可以通过系统接口为其他 ADMIN 账号授予或撤销受支持的业务能力；每项授权须限定学院范围（可进一步限定批次），并记录授权依据、操作者、时间和撤销信息。常规授权接口不得授予、转移或撤销 `ADMIN_ACCOUNT_MANAGER`（管理员账户管理能力）；该能力仅能由系统初始化配置，或按 TODO-24 的应急恢复流程处理。业务授权不改变目标账号的 ADMIN 角色，也不自动扩大目标账号在授权范围之外的数据访问权。

## 4. 补充确认事项

以下条目分别由文档审查（`TODO-18`～`TODO-26`）、复审（`TODO-27`～`TODO-32`）、后续边界复核（`TODO-33`～`TODO-35`）与逻辑建模评审（`TODO-36`～`TODO-42`）提出，均已确认。

- **TODO-18 批量录取的结案与明细**：批量录取依次录取至名额用尽；因名额不足未录取的余项结案为 `NOT_ADMITTED`，响应须返回每项成功/失败明细，并在界面提示「名额不足，部分未录取」，不得超额。排序键见 TODO-27。
- **TODO-19 禁止启动后的处置**：批次在 `SCHEDULED` 状态且已错过全部阶段时禁止启动；管理员可执行「撤回发布」（`SCHEDULED → DRAFT`）重新配置时间后再次发布，或直接取消批次。撤回发布为独立操作并记录审计。
- **TODO-20 导出范围与简历保护**：导师导出仅限本人当前及已处理申请的名单字段（姓名、学号、专业），不含简历；简历仅可在系统内经受控鉴权接口在线查看。管理员导出简历须单独授权、限定范围并留痕；成绩默认不可导出。
- **TODO-21 批次唯一性（由 TODO-34 细化）**：同一学年、同一学院同时最多一个运行批次；准确的运行状态范围、终态批次是否占用名额及追加批次规则见 TODO-34。同一学生同一学年只允许一个 `MATCHED` 关系。
- **TODO-22 暂停的顺延计算**：暂停时长累计计算；暂停发生在某阶段时，该阶段及所有未开始阶段整体平移累计暂停时长；尚未配置时间的未来阶段（如未开启的补选）在其配置时按与原阶段的相对间隔顺延，并以冻结时刻为基准。
- **TODO-23 未提交者补选资格的政策说明**：允许填报截止时未提交志愿的学生参加补选，属于有意的业务取向——以提升整体匹配率、减少漏报为目标，不视为对缺席的否定性评价。
- **TODO-24 总管理员应急恢复**：总管理员账户仅设一个。为防范离职或失联导致无人可管理管理员账户，须在运维文档中定义应急恢复流程：由学校主管部门线下核验身份后重置凭证或移交账户，操作须双人复核并全程留痕；该流程不改变总管理员的业务权限范围。
- **TODO-25 学生匹配状态的作用域**：学生匹配状态按批次持有（以「批次 + 学生」为维度），不设跨批次的单一全局状态；各文档中原有的「全局匹配状态」统一修正为「本批次匹配状态」。跨批次的整体视图为派生结果，不作为状态存储。`UNMATCHED` 的来源包括三轮结束、填报截止未提交、批次取消、启动时所有已填志愿轮次均已跳过，以及管理员撤销关系；状态值相同，具体来源及后续可办理范围由所属批次状态决定。
- **TODO-26 字段级可见性清单**：在权限矩阵中补充学生资料字段的可见性矩阵。默认：学生本人可见并维护本人可编辑字段；导师可见姓名、学号、专业、学位类型、个人简介、简历，**不可见**联系方式与成绩；管理员按任务最小化可见姓名、学号、专业、学位类型、个人简介、简历，联系方式仅在通知等必要业务场景下由授权管理员查看并留痕；成绩首期不采集、不展示（TODO-42）。学位类型由 2026-10-01 的 TODO-43 补充，用于核对可报资格；不自动扩大 TODO-20 的导出字段。

- **TODO-30 人员名单导入与数据同步**：首期不接外部系统，由管理员使用 Excel/CSV 模板导入并手工维护；学生以学号为唯一标识，导师以工号为唯一标识；导入须生成批次记录与错误报告（重复、缺失、格式不符）。

- **TODO-32 统计口径**：分母为符合资格学生总数（含未提交者）；未提交、启动时所有已填志愿轮次均已跳过、关系纠错或身份纠错导致未匹配均单列，不计入正常志愿流程未匹配；批次取消单独标记，不纳入正常完成率。少于三项志愿者耗尽已填顺位后仍未匹配者计入正常志愿流程未匹配，可按实际耗尽轮次细分（TODO-37）。志愿按最终锁定版本计一次；补选单列（补选录取数、补选后仍 `UNMATCHED` 数）；导师名额使用率 = 已锁定关系 / 名额上限。报表同时提供当前 `UNMATCHED` 总人数及正常志愿流程未匹配人数，并可按上述来源拆分。
- **TODO-33 启动时跳过阶段后的处理**：已错过阶段关闭且不补办。首个实际开放轮次为第 N 轮时，当前轮只处理仍未匹配且已锁定第 N 志愿的学生；后续轮次仍按原优先级顺序处理。此前被跳过的已填志愿记录为 `SKIPPED_BY_SCHEDULE`，不得记作导师不录取；学生没有任何尚未错过的已填志愿时，转为 `UNMATCHED`。填报窗口已结束时不得补交或修改志愿；没有提交志愿的学生按未提交规则置为 `UNMATCHED`。跳过阶段不改变批次手动启动、按当前时间进入阶段和错过全部阶段不得启动的规则。
- **TODO-34 同学年批次唯一性的运行范围**：同一学年、同一学院同时最多一个处于 `SCHEDULED`、`ACTIVE` 或 `PAUSED` 的运行批次。`DRAFT`、`COMPLETED`、`ARCHIVED`、`CANCELLED` 不占用运行名额；前一运行批次进入终态后可创建后续批次。首期不支持同学年多个运行批次并行；追加批次仍须管理员显式创建并记录原因。同一学生同一学年只允许一个有效 `MATCHED` 关系。
- **TODO-35 已完成/归档批次的关系纠错**：批次 `COMPLETED` 后不再接受常规学生/导师办理，但授权范围内具备关系管理权限的管理员仍可执行有原因、有审计的关系撤销、恢复或改派；操作须重新校验关系、学生状态和导师名额，并同步更新名额及统计，不重新开放轮次或补选。单独撤销关系使学生转为 `UNMATCHED` 时须记录来源 `RELATION_REVOKED`，统计中与三轮结束未匹配区分。`ARCHIVED` 批次只读；纠错前须经审计操作解除归档，转回 `COMPLETED`，完成纠错后可再次归档。总管理员身份本身不额外授予关系管理权限。
- **TODO-36 志愿版本唯一性**：每次完整志愿提交生成新版本；同一版本内志愿顺位和导师均不得重复。唯一性作用域为「批次 + 学生 + 志愿版本 + 顺位」及「批次 + 学生 + 志愿版本 + 导师」，不得对同一学生的全部历史版本施加「批次 + 学生 + 顺位」唯一约束。全历史保留；每位学生同批次最多一个最终锁定版本。
- **TODO-37 少填志愿后的耗尽原因与统计**：少于三项志愿者在其最后一个已填顺位轮结束后仍未匹配，原因记录为 `PREFERENCE_EXHAUSTED`，同时保存实际最后轮次/顺位；不将第一或第二轮耗尽伪记为 `ROUND3_EXHAUSTED`。该类计入正常志愿流程未匹配，可按实际耗尽轮次细分。未提交、阶段全部跳过、关系纠错及批次取消仍按各自已确认口径统计。
- **TODO-38 轮次重开时的自动结案恢复范围**：满足 TODO-14 的重开前置条件时，只恢复该轮因截止而被系统自动结案、且没有导师明确决定的 `NOT_ADMITTED` 申请；批量操作中因名额不足而结案的项目不属于此范围。保留原自动结案事件并追加被重开取代的事件，将该申请恢复为 `IN_REVIEW`；仅因本次自动结案推进的学生匹配状态恢复到该轮处理前状态，后续轮次中仅自动生成且无人处理的申请标记为被重开取代，不再参与当前队列。导师明确不录取、已录取关系及任何已有后续轮处理动作均不得回滚。
- **TODO-39 补选决策与批次完成**：管理员须在批次发布前决定是否安排补选；安排补选时，须在发布前配置开放时间，发布后不得新增补选安排。补选窗口关闭时仍待处理的申请按 TODO-07 结案，补选窗口关闭即将批次置为 `COMPLETED`；不得重开已关闭的补选窗口，若需调整须在窗口关闭前完成。批次完成后不得追加补选安排，符合 TODO-35 的完成后纠错边界。
- **TODO-40 申请资料版本**：学生资料在对应申请实际进入 `IN_REVIEW` 时形成该次处理的资料快照；补选申请提交即进入待处理时形成快照。快照字段限姓名、学号、专业、学位类型、个人简介和当时的简历附件版本；不包含联系方式与成绩。学位类型由 2026-10-01 的 TODO-43 补充；轮次重开产生新的处理周期/快照，原快照和处理历史保留；快照不改变资料访问授权。
- **TODO-41 批次资格名单与统计分母**：在填报窗口开放时冻结该批次的合格学生名单和统计分母，纳入当时符合资格且账号启用的学生（含之后未提交者），排除同学年其他批次已有有效 `LOCKED` 关系的学生。此后资格或账号变化不自动回算分母；漏纳/误纳名单只能由授权管理员显式更正并记录前后值、操作者、时间和原因，统计依据为冻结名单及审计更正历史。
- **TODO-42 成绩与毕业日期**：首期不采集或展示成绩，后续若纳入另行确认数据来源和范围。简历保留期按学生经学校确认的毕业日期计算，毕业日期由授权管理员依据学校确认的信息维护并留变更记录；毕业日期缺失或未确认时不自动删除简历，待日期确认后再计算保留截止时间。

### 4.1 API 与并发语义（2026-10-02 已确认）

- **TODO-50 阶段截止时刻的操作生效边界**：时间字段通过带偏移的 RFC 3339 格式传输，服务端按 UTC 瞬时保存和比较，界面按 `Asia/Shanghai` 展示。填报、轮次和补选窗口均采用左闭右开区间 `[startAt,endAt)`；服务端先锁定阶段记录，再读取数据库 UTC 时间作权威校验，客户端时间不参与。恰好等于 `endAt` 时拒绝。若事务内校验时刻早于 `endAt` 且校验通过，即使事务在 `endAt` 之后提交，该请求仍有效。异步批量请求逐项执行时，每项按自身事务的阶段校验时刻判定；仅接收批量请求不代表其中项目已在截止前办理。
- **TODO-51 不同批量操作竞争名额的顺序**：一次批量操作内部继续按 TODO-27 的业务排序键串行处理；不同批量操作之间不建立全局排序或 FIFO 队列。名额行锁与事务保证不超额，竞争最后一个名额时由先取得名额行锁并成功提交的操作取得；不承诺跨请求公平顺序。

## 6. 数据设计输入约束（不新增业务规则）

以下条目是**逻辑模型、数据字典与建表设计的强制输入**，由第 3、4 节已确认规则推导而来；物理实现提示不等同于已选定数据库约束方案。

1. **状态来源可追溯：** 学生-批次状态须记录进入原因（`ROUND3_EXHAUSTED` / `PREFERENCE_EXHAUSTED` / `NOT_SUBMITTED` / `BATCH_CANCELLED` / `ALL_REMAINING_PREFERENCES_SKIPPED` / `RELATION_REVOKED` / `IDENTITY_CORRECTION`）及发生时间；志愿耗尽须记录实际末轮/顺位。`UNMATCHED` 各来源在状态值上相同，若不留存原因，TODO-32 的当前未匹配总数和正常流程未匹配分类将失去依据。
2. **志愿版本完整留存：** 须保留志愿的全部版本、各版本提交时间与锁定标记，以支撑 TODO-27 的排序键与 TODO-03 的历史追溯。
3. **历史不可覆盖：** 逐轮处理记录（学生 × 轮次 × 结果）、师生关系历史、名额变动流水、审计日志、通知记录各自独立留存，不覆盖既有记录。名额上限及占用余额在 E17 维护，师生有效关系 E24 为关系事实依据，E27 为不可覆盖的名额变动核对流水；录取/撤销/恢复等关系变更与余额、流水须在同一事务内保持一致。
4. **排序键可复现：** 所有批量操作的排序键必须可确定、可持久化，禁止依赖界面顺序或不可复现的运行时顺序。
5. **唯一性与并发约束：** `批次 + 学生` 状态唯一；`批次 + 学生 + 志愿版本 + 顺位` 及 `批次 + 学生 + 志愿版本 + 导师` 唯一，全历史版本保留；`批次 + 学生` 有效关系唯一且同学年有效关系唯一；补选「同一时刻最多一条待处理申请」唯一约束；录取的名额扣减与关系建立须以适合所选数据库的条件更新/事务并发控制保证不超额、不重复匹配。
6. **阶段跳过结果可追溯：** 被跳过的已填志愿与未提交志愿、导师不录取须可区分，至少保留批次、学生、志愿顺位、结果原因和发生时间；`SKIPPED_BY_SCHEDULE` 不得计入导师不录取统计。
7. **运行批次唯一性：** 按 TODO-34 的运行状态范围实施同学年、同学院最多一个运行批次的唯一性约束；已完成、已归档和已取消批次保留历史，但不阻止创建后续批次。
8. **关系例外事务：** 完成/解除归档后的关系纠错必须保留关系历史、审计原因、操作者和前后状态，并与名额及统计更新保持一致。
9. **资格名单快照：** 填报窗口开放时记录合格学生与账号状态快照；追加批次排除同学年已有有效匹配者；名单更正留审计，统计不随当前账号状态自动回算。
