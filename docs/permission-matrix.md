# 权限矩阵

> 版本：1.0（已确认设计基线）  
> 状态：业务方确认按当前内容定案；角色、数据范围和字段访问均以本矩阵为准。  
> 本矩阵区分学生、导师和管理员业务权限。总管理员是计算机学院管理员之一，与其他管理员拥有相同业务权限，额外负责管理员账号及其业务能力授权管理；不另设校级管理员。

## 1. 权限标记

- **允许：** 该角色在身份、时间和业务状态校验通过后可执行。
- **本人：** 仅限本人账号、资料、志愿或结果。
- **当前申请：** 仅限当前轮投给该导师的学生申请。
- **授权范围：** 仅限管理员被授权的批次/学院范围。
- **禁止：** 普通业务流程不得执行。

> 授权范围与字段级细节的决策依据见 [待确认事项登记表](todo-register.md)；学生资料字段的逐项可见性另见第 5 节。

矩阵中的“管理员”列表示计算机学院管理员业务权限，总管理员同样适用。管理员账号创建/重置及其他 ADMIN 账号的业务能力授予/撤销仅由总管理员执行；该身份不额外授予其自身批次、名额或关系处理权限。

服务端对每次请求执行权限和对象范围校验；前端隐藏按钮不能替代后端授权。

## 3. 管理员角色与范围

当前由计算机学院管理员管理本学院业务，不另设校级管理员。系统设一位总管理员，该账户属于管理员，与其他管理员有相同业务权限，另负责管理员账户生命周期及为其他 ADMIN 账号授予/撤销普通业务能力；该身份不增加其自身的名额或已锁定关系处理权限。管理员账户的创建/重置仅由总管理员执行并全程审计，凭证为随机一次性临时凭证、有效期 72 小时、仅一次性展示并由管理员线下转达，首次登录强制改密。权限点包括：

- **批次管理：** 创建、发布、暂停和结束批次。
- **人员管理：** 创建账号、维护导入名单和人员状态。
- **规则管理：** 配置资格、志愿数、轮次时间、导师名额和补选时间。
- **结果管理：** 查看匹配结果并处理授权异常。
- **数据导出：** 导出名单与统计。
- **审计查看：** 查询敏感操作记录。

**已确定：** 总管理员属于管理员之一，业务权限相同，仅额外拥有管理管理员账户的权限；不另设校级管理员。关系例外由具备相应业务权限的管理员在授权范围内处理并留痕。**BR-10（已确认）：** 管理员账户的创建/重置仅由总管理员执行并全程审计；凭证为随机一次性临时凭证，有效期 72 小时，仅一次性展示并由管理员线下转达，首次登录强制改密，不通过邮件或短信发送（TODO-31）。**应急恢复（TODO-24）：** 总管理员账户仅设一个，须由学校主管部门线下核验身份后执行凭证重置或账户移交，双人复核并全程留痕；该流程不改变总管理员的业务权限范围。

**管理员业务授权（TODO-52，2026-10-03 已确认）：** 仅总管理员可以向其他 ADMIN 账号授予或撤销普通业务能力，且须明确学院/可选批次范围并保留完整审计。常规 API 不得授予、转移或撤销 `ADMIN_ACCOUNT_MANAGER`；仅系统初始化或 TODO-24 应急恢复流程可设置该能力。

## 4. 字段级访问原则

1. 学生仅查看本人敏感信息和本人互选状态。
2. 导师只能查看当前批次中申请过本人的学生资料，字段限于姓名、学号、专业、学位类型、个人简介和简历；其他学生不得查看他人资料、成绩或简历。
3. 学生简历只能经受控鉴权接口访问，不提供免鉴权的公开下载地址。管理员按授权范围查看。
4. 匹配记录、申请记录和关键审计记录长期保留；简历附件保留至学生毕业后 5 年（以学校数据管理要求为准），期间不自动删除历史附件。
5. 管理员按任务最小化查看个人资料；结果导出应限字段、限范围并留痕。
6. 导师公开资料需区分公开字段和内部维护字段；学生可见导师「是否可填报」布尔值，不显示具体剩余名额，目录提供研究方向、姓名或工号、「是否可填报」三项筛选（TODO-28）；导师联系方式不公开。
7. 角色或组织范围变更应立即影响后续请求权限；已导出的数据不能由权限系统收回，因此导出前需再次授权。
8. 简历留存截止根据经学校确认的毕业日期计算；授权管理员维护毕业日期及变更记录。日期缺失或未确认时不自动删除简历。
9. 学生目录的“是否可填报”结合该学生的专业和学位类型判断；查看导师公开范围不赋予查看其他学生身份信息的权限。范围配置与导师介绍的公开审核分开表达，不能由 TODO-P07 自动推定可报范围审批政策。
10. 填报开始后管理员按 TODO-48 更正学生身份时，如已有匹配关系须撤销并释放名额，该生跳过剩余常规轮次、变为 `UNMATCHED` 并等待补选；不得由导师或学生自行撤销关系。无补选窗口等低概率边界暂缓，本期不处理（TODO-49）。
